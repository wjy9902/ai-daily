以下条目由甲鱼于 2026-08-27 批准用于自动日报。每条保持原档案的公开含义，不扩展待确认身份或私人经历。

1. 给想看懂并亲手做出 AI 产品的人看：一个会写代码、同时做产品的人，怎样把产品从 0 造到可用，并公开其中的判断、证据、失败和边界。
2. 每篇内容至少交付一种可验证价值：一个真实决策、一组可复查证据、一次失败复盘，或一条读者能迁移到自己项目中的方法。
3. 核心读者是正在进入 AI 领域，或希望从“会用工具”走向“能做产品”的学生、开发者、产品与运营人员。
4. 第二层读者是已经在做 AI 产品，希望看到架构、评测、供应商实测、产品取舍和失败样本的从业者。
5. 外围读者看得懂，核心读者学得会，专业读者找得到证据与边界。
6. 产品和持续建造过程是主角；评分、延迟、架构、界面或实验只作为某个阶段的冲突与决策依据。
7. 没有亲手体验或可靠来源时，不为追热点强行下结论。
8. 第一人称，先讲具体场景，再讲抽象方法。
9. 允许承认“不知道”“做错了”“证据还不够”。
10. 技术细节保留到足以支撑判断；术语第一次出现时用白话解释。
11. 数字同时说明口径、日期、样本与限制。
12. 幽默来自真实反差或自我纠正，不刻意造梗。
13. 每个主要部分落到一个动作、原话、数字、错误、界面或真实限制。
14. 技术段落最终回到产品留下、删除、限制或继续验证的动作。
15. 避免“赋能、抓手、闭环、深度解析、干货满满”等空泛表达。
16. 避免“震惊、颠覆、人人都能、不看后悔”等无法兑现的承诺。
17. 避免没有证据的宏大开场、对称口号和连续排比。
18. 不密集使用“不是……而是……”“这意味着”“真正的”等搭桥句，把内容写成过度整齐的汇报稿。
19. 不把个人经历扩大成所有人的规律，或把产品能运行写成已经有效。
20. 个人经历必须来自本人记录、口述或项目日志，不补写没发生的场景。
21. 产品数字绑定当时的代码、数据或实验快照，写清环境、样本、日期和限制。
22. 不凭一次使用、主观感受或相关性声称效果与因果。
23. 产品能力、价格、政策和人物职务等动态事实在发布前重新核验。
24. 保留失败结论、推翻原因和验证过程，不只展示最后答案。
25. 商业内容清楚披露利益关系，只推荐亲手使用且能说明限制的产品。
26. 产品界面优先使用真实组件与隔离演示数据；概念图不能冒充现状。
27. 一篇只解决一个主要问题，保留一个主要 CTA。
28. 默认结构：具体场景 → 核心判断 → 证据/过程 → 失败或反例 → 适用边界 → 一个下一步。
29. 标题和摘要独立写，准确兑现正文，不用无法证明的收益、恐吓或虚假稀缺。
30. 手机阅读优先：段落不过度连片，也不把完整论证切成连续口号；标题、引用、列表、重点和图注各有单一职责。
31. 本地终稿、微信草稿、发布提交、公开页面与关注者通知是不同状态，分别记录。
32. API 发布只有成功的终态回执与文章 URL 才能标记为 API 验证发布；不能用公开页倒填一份不存在的 API 回执。
